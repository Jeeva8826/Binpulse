# BinPulse / EcoRoute User Guide

This guide is for someone opening the project for the first time. The dashboard keeps simulated ward history separate from physical sensor readings. The optional BIN01 monitor uses an Arduino Uno over USB; the separate yard entrance node uses an ESP32 over Wi-Fi.

## 1. Know which readings are real

- **Demo history** is generated by the project for nine Coimbatore areas. It supports the analytics, schedule, route, and report screens, and is labeled simulated.
- **EcoRoute Sample Data** contains the two supplied JSON example records. It is also simulated and does not train a model.
- **The yard ultrasonic sensor** reports distance to an object and the estimated presence of a truck at one fixed location. The displayed truck load is an estimate based on the truck-bed settings.
- **The Arduino Uno BIN01 sensor** reports a live bin fill level over USB serial. These readings are stored separately from the simulated ward history.
- One yard sensor does not provide GPS tracking or actual area-by-area weights. Those require GPS hardware and weighing/collection data sources.

## 2. Start the dashboard on Windows

1. Install **Node.js 22 or newer**. This project uses Node's built-in SQLite support.
2. Open PowerShell in the project folder, `BINPULSE PROJECT`.
3. Install the project packages (first run only):

   ```powershell
   npm install
   ```

4. Create or restore the demo history:

   ```powershell
   npm run seed
   ```

   This provides about eight weeks of simulated history for nine areas. You can run it again later to reload the demo baseline.

5. Start the backend and dashboard:

   ```powershell
   npm run dev
   ```

6. Open **http://localhost:3000**. Keep the terminal open while using the app. Press **Ctrl+C** there to stop both services.

## 3. Recommended first walkthrough

1. **Overview** — check the area summary, scheduled collections, route savings, and yard connection status.
2. **EcoRoute Sample Data** — inspect the two supplied records and their simulated-data labels.
3. **Area Analytics** — view category totals, the 30-day intake trend, and the ward classification rationale. Rule-based statistics are the default. The light-ML option needs at least four weeks of history and must be enabled in Settings.
4. **Smart Schedule** — inspect the weekly area/day grid. Select a cell to read why a collection was scheduled. Use **Regenerate Weekly Plan** after changing settings or demo data.
5. **Route Planning** — choose a day and truck capacity, then select **Recalculate Route**. The map and itinerary use the generated schedule and configured depot/yard coordinates.
6. **Driver Dispatch** — select a truck, driver, waste category, and one or more areas; then dispatch. Mark the trip complete when it returns. A real yard arrival/departure can also finish an active trip.
7. **Yard Entrance Node** — use **Inject Single Sensor Sample** for one simulated reading, or **Trigger Arrival → Dwell → Departure** for a complete demo visit. These controls do not use the physical sensor.
8. **Manifest & Reports** — review aggregate estimates and choose **Export Manifest (CSV)** to download a report.
9. **Alerts & Risks / System Settings** — resolve alerts and adjust sensor thresholds, waste densities, health-gap limits, attribution, or ML mode. Select **Save Configuration** after edits.

The top **Simulation / ESP32 Yard** selector controls the central Yard Entrance Node view. Simulation mode shows simulator readings and test controls. ESP32 Yard mode shows physical ESP32 yard readings. The **Arduino Bin Monitor** is separate: it reads BIN01 over USB whether or not the yard selector is changed.

## 4. Run a continuous software-only sensor demo

Leave `npm run dev` running. Open a second PowerShell window in the project folder and run:

```powershell
npm run simulate
```

The simulator sends changing ultrasonic distances to the local backend about every two seconds. Open **Yard Entrance Node** and watch the reading and truck-presence status. After a short idle period, it simulates an approach, dwell, and departure. Press **Ctrl+C** in the second window to stop it. Do not run this stream when you are trying to verify physical-only readings.

## 5. Connect the Arduino Uno BIN01 sensor

1. Wire HC-SR04 **VCC to 5V**, **GND to GND**, **TRIG to D7**, and **ECHO to D9**. The Uno accepts 5V on its digital input; this differs from the ESP32 wiring.
2. In `firmware/binpulse_bin_node/config.h`, calibrate the bin size and empty/full distances to match the installed sensor.
3. In Arduino IDE open `firmware/binpulse_bin_node/binpulse_bin_node.ino`, select **Arduino Uno** and **COM12**, then upload. The sketch streams JSON at **115200 baud**.
4. Start BinPulse with `npm run dev`. The backend reads COM12 and the dashboard uses port 3000. Close Arduino IDE Serial Monitor while BinPulse is reading the serial port.
5. Open **Arduino Bin Monitor** in the dashboard. The live card shows BIN01 fill, distance, volume, and last-reading time; other bin cards are labeled sample values.

The backend defaults to `ARDUINO_SERIAL_PORT=COM12` and `ARDUINO_BAUD_RATE=115200`. Set these in `.env` if the assigned port changes. For details, see [REALTIME_BIN_SETUP.md](REALTIME_BIN_SETUP.md).

## 6. Connect the ESP32-S3 yard sensor

1. Use an HC-SR04-compatible sensor. Connect sensor **VCC to 5V/VIN**, **GND to GND**, **TRIG to GPIO 43**, and **ECHO to GPIO 44 through a voltage divider**. Do not connect the sensor's 5V ECHO directly to an ESP32 pin. The provided 1 kΩ series / 2 kΩ to GND divider reduces it to a safe logic level.
2. On the laptop, find its Wi-Fi IPv4 address with `ipconfig`. The board and laptop must be on the same network.
3. Edit `firmware/binpulse_yard_node/config.h`: enter the Wi-Fi name/password and set the server URL to `http://<laptop-ip>:5000/api/device/readings`. Use the API key that matches the backend's `DEVICE_API_KEY` setting.
4. Keep `npm run dev` running. In Arduino IDE open `firmware/binpulse_yard_node/binpulse_yard_node.ino`.
5. Select **Tools → Board → esp32 → ESP32S3 Dev Module** (not the classic **ESP32 Dev Module**) and the COM port assigned to your board. Enable **USB CDC On Boot** if that option is present, then upload.
6. Open Serial Monitor at **115200 baud**. Confirm Wi-Fi connects and HTTP requests succeed. Switch the dashboard to **ESP32 Yard** and open **Yard Entrance Node**. The node should change from **WAITING FOR DEVICE** to **DEVICE ONLINE**, and the distance/last-reading time should update about every two seconds.

Use [NEXT_STEPS.md](NEXT_STEPS.md) for the detailed wiring and upload procedure. The yard firmware is not needed for the Arduino Uno BIN01 monitor.

## 7. Reload, reset, and test

- **Reload Demo Data** restores the simulated baseline while preserving sensor records. Use it if the charts have too little history or demo records were changed.
- **Reset** asks for confirmation, clears simulated history, then restores the demo baseline. Physical ESP32 sensor readings are preserved.
- Run `npm test` to execute the isolated software/API/workflow tests. Tests use a temporary database and do not alter the dashboard data.
- Run `npm run build` to verify/build the production frontend. To run that build locally, use `npm start` and open **http://localhost:5000**.

## 7. Troubleshooting

| What you see | What to do |
|---|---|
| Analytics shows too little history | Select **Reload Demo Data**, wait for refresh, and reopen Analytics. |
| Arduino Bin Monitor is waiting | Confirm the Uno is on COM12, close Arduino IDE Serial Monitor, and restart the backend. |
| ESP32 yard node is OFFLINE | Confirm the board is powered, on the same Wi-Fi, using the laptop's current IP, and posting to port 5000. |
| Upload says “This chip is ESP32-S3, not ESP32” | Select **ESP32S3 Dev Module** in Arduino IDE. |
| No ultrasonic readings | Check common ground, the selected sketch's TRIG/ECHO pins, sensor orientation, and board-appropriate voltage levels. |
| Browser cannot open the dashboard | Keep `npm run dev` running; check that ports 3000 and 5000 are available. |
| Map tiles are missing | The map background needs an internet connection; the route summary remains available without tiles. |

For physical limitations and estimation assumptions, see [LIMITATIONS.md](LIMITATIONS.md).
